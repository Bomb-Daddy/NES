# EXEC0092 — Strictly counterfactual first PPUSTATUS source tracing, 0.92.0-dev1

This continues the **entire inherited EXEC0091 C11 native game and all prior mechanics**. The precise archived fresh Mesen AllZeros RAM setting was previously verified and the SHA-256-verified original USA ROM reached PPUSTATUS `$2002` at PC `$C5BE` after 142 CPU instructions. Those 142 original-ROM instructions are **source-derived**, not a new Mesen runtime replay.

The new `gk92_trace_reset_ppustatus_hypothesis` accepts 1..256 explicitly hypothetical PPUSTATUS read bytes and runs the existing bounded original-ROM 6502/MMC1 interpreter, consuming one byte only on an address mirrored to `$2002`. After the provided bytes are exhausted, any further peripheral read refuses. Valid ROM SHA, input count and pointers, maximum instructions, and output atomicity are checked. `Gk83Trace.hypothetical_ppustatus_reads` makes simulated reads explicit. Normal `gk91_trace_reset_mesen_allzeros` behavior is **unchanged** and still stops at `$C5BE` without any guessed PPU value. No `PPUSTATUS` low-bit open bus, real VBlank transition or 6502/PPU cycle timing is simulated. **Do not mistake this branch exploration for authentic runtime observations or first Spring generation.**

To test authenticated original privately: `GK1_ORIGINAL_STOCK_ROM=/private/stock.nes ctest --test-dir build --output-on-failure -R GK1_092`. Tests without private ROM cover argument rejection; with it they verify the bounded source execution and deterministic counterfactual paths. No original ROM, screenshots, RAM captures, audio, or licensed files belong in this public tree.

The original first playable Spring, all twelve locked commands, AI, dynasty, Trade schedule, Win32 native execution and physical Xbox remain OPEN. Next original source breakthrough requires timing/data from a matched Mesen PPUSTATUS read or source-derived register/clock model, not fictional values.

Exact original ROM in source-only hypothetical test: first `$2002` return `0x00` reaches the *next* hardware gate after 144 completed CPU instructions; first return `0x80` reaches it after 271 instructions. Both stop at PC `$C5BE` again, requiring another PPUSTATUS value. These are alternate ROM branch paths for caller-chosen status, not observed PPU values or cycle-accurate runtime.

Additional source-side constrained result: archived fresh Mesen config omits `RandomizeMapperPowerOnState`; MesenCE `Core/Shared/SettingTypes.h` defaults that to `false`, and its `Core/NES/NesPpu.cpp` clears the PPU status flags at true cold reset in that mode. The first PPUSTATUS read is within at most `142 × 7 = 994` source-interpreted 6502 cycles, far before the earliest NTSC PPU first VBlank (~27,384 CPU cycles per NESdev PPU power-up reference). Therefore bit 7 of that **first** status is zero for this *specific* configured fresh Mesen experiment, while bits 0–4 remain unknown PPU open bus. Actual original-ROM code paths have been checked for all 32 hypothetical low-bit combinations and all converge on `$C5BE` again after 144 completed instructions. This strengthens first-branch *control flow*, **not** precise PPU register values or original runtime parity.
